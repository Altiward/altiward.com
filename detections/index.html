Detections for Sentinel and Splunk

altiward-siem holds analytics rules, hunting queries and saved searches for the OCSF records Altiward and altiward-forwarder send. Every field each one reads is checked against example records from both projects.

View detections on GitHub Deploy the Sentinel rules

Free and open source under Apache 2.0. Set up the Sentinel table first, as Altiward's Sentinel guide describes.

Thirteen rules and searches

Each runs in your SIEM, as a Sentinel rule or hunting query and a Splunk search. They read the events Altiward or altiward-forwarder sends; the forwarder sends grants and revocations only, so most need Altiward.

The admin-time rule is a template: set the limit at the top of the query. 120 minutes a day is the default. To report the same limit as SAP Privileges 2.7's AdminBudget, use the same number. The rule adds up time on the server's side, so it works on any Privileges version, covers someone's Macs together, and isn't reset by moving a Mac's date forward.

Install in Sentinel or Splunk

Microsoft Sentinel
Deploy every analytics rule at once with the Deploy to Azure template, or create one from its YAML. Paste a hunting query into Logs. The rules read the AltiwardOCSF_CL table, which Altiward's setup script creates; altiward-forwarder uses the same table.
Splunk
Copy savedsearches.conf into one of your apps. The alerts and reports start switched off: enable the ones you want and add an alert action. Each search is also a file to paste into Search.
Checked against real records
CI checks every field a detection reads against example OCSF records from Altiward and altiward-forwarder, so a rule can't depend on a field neither project sends.
