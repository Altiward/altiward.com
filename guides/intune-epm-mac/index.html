Intune EPM on Mac: what to use instead

Intune's Endpoint Privilege Management (EPM) doesn't support macOS. This guide explains what Intune shops use on Macs instead, then shows how to deploy SAP Privileges, and optionally Altiward, through Intune.

Last reviewed October 2026Microsoft IntuneSAP Privileges 2.6.0macOS 13 or later

Does Intune EPM work on Macs?

No. Microsoft documents Endpoint Privilege Management for Windows only. Its EPM overview, updated 2 October 2026, says it applies to Windows, and EPM elevates only .exe, .msi and .ps1 files. Intune's features in development list, updated 30 September 2026, has no EPM for macOS.

On Windows, EPM lets a standard user run approved files with elevated rights, using rules you set in Intune, and logs each elevation. Intune has nothing like it for Macs. What Intune does offer on macOS is a managed local admin account created at enrollment, with its password held in Intune. That account is for IT, not a way for people to get admin rights for a task.

What to use on Macs instead

Most Mac fleets that remove everyday admin rights use one of two approaches.

ApproachHow it worksCost
SAP PrivilegesThe person asks for admin, optionally gives a reason, and gets full admin rights for a time you limit. You configure it with an MDM profile, and it can send each change to syslog or a webhook.Free, open source (Apache 2.0)
Commercial endpoint privilege tools with a Mac agent, such as Admin By Request, BeyondTrust and CyberArkCloser to EPM on Windows: rules for which apps can run elevated, approval workflows and central reporting.Paid, per device or user

The main difference from EPM: Privileges gives the person full admin for a period rather than elevating one app. Its timer runs in that person's own session, and an admin can stop it. When SAP Privileges admin rights outlive the timer covers the causes and the settings that narrow them. If you need something outside the session to check who holds admin and remove expired rights, add Altiward (below).

Deploy SAP Privileges with Intune

All of this is in the Microsoft Intune admin center. Test on a pilot group before assigning it to everyone.

  1. Add the package. Download Privileges_<version>.pkg from SAP's releases (2.6.0, released 17 September 2026, at the time of writing). In Intune, go to Apps › All Apps › Create, choose platform macOS and type macOS app (PKG), and upload it.
  2. Approve the system extension and its access. SAP's example profiles include Example_ApprovePrivileges.mobileconfig. It allows SAP's system extension (team 7R5ZEU67FQ), gives corp.sap.privileges.extension Full Disk Access, and manages Privileges' login items and notifications. It also sets two Privileges keys, RevokePrivilegesAtLogin and EnableSystemExtension: delete its Privileges configuration payload and put those keys in the next step's settings instead, so that only one profile sets corp.sap.privileges. Upload the edited file at Devices › Manage devices › Configuration › Create › New policy, platform macOS, profile type Templates › Custom, deployment channel Device channel.

  3. Set Privileges' settings. Create another macOS policy with Templates › Preference file and preference domain name corp.sap.privileges. Intune wants the keys alone, without the <?xml, <!DOCTYPE and <plist> lines or the outermost <dict>. SAP's Managing Privileges page documents every key, and the expiry guide explains which ones narrow the gaps. A starting point:

    That example limits each grant to 30 minutes, requires a reason, turns on Privileges' tamper protection and removes rights at the next login. To send Privileges' own events to your SIEM, add RemoteLogging to the same file; see SAP Privileges events in your SIEM.

  4. Check a pilot Mac. Under System Settings › General › Device Management, both profiles should be listed. Request admin in Privileges, check that the duration matches your limit, then run PrivilegesCLI --history --privilege-changes-only to see the grant recorded.

Intune will need macOS 15 or later for new enrollments once Apple releases macOS 27, according to Microsoft's development notes. Macs already enrolled stay enrolled.

Add Altiward for oversight

Privileges grants admin, and Altiward checks it. Altiward's agent reads each Mac's admin group, compares it with the grants Privileges reported, and alerts on rights past their expiry, or removes them if you turn enforcement on. It sends the evidence to your SIEM. It needs an Altiward server first: follow the install guide, which also lists what leaves each Mac. Then, in Intune:

  • Agent settings: a Templates › Custom policy, device channel, with com.altiward.agent.mobileconfig, a ready-made profile that Intune accepts without conversion. Edit your copy first: ServerURL, EnrollmentToken, PermanentAdmins and ExpiryEnforcement (alert by default, or enforce to remove overdue rights), and the rest as its comments explain. Leave MDMDeviceID as {{deviceid}}, which Intune fills in with each Mac's device ID.
  • Login items: a Templates › Custom policy, device channel, with altiward-login-items.mobileconfig, so people can't turn the agent off.
  • The package: Altiward-<version>.pkg from GitHub Releases, added as macOS app (PKG).
  • The hook: add the keys from the agent release's corp.sap.privileges.plist to your existing Privileges preference file. PostChangeExecutableChecksum must match the agent version you deploy, or Privileges won't run the hook. Leave PostChangeActionOnGrantOnly unset, because Altiward needs revokes too.

To create the agent settings and login items policies in one go, run Push-AltiwardProfiles.ps1 from the server release's integrations/intune/ folder. It signs in as you, creates the policies (or updates them when you run it again) and assigns them to a group. Run it with -WhatIf first, and leave out -PrivilegesSettings when Privileges' settings are already in a preference file, as in this guide. Its README lists the permissions it asks for.

Assign Privileges and Altiward to the same groups. The script assigns only Altiward's policies, so add the Privileges app, its settings and its system extension profile to that group yourself, and assign none of them more widely: a Mac with Privileges but no Altiward lets people become admins with nothing recorded. To stop a person or a Mac getting admin, see Stop someone getting admin with SAP Privileges.

Privileges has one hook setting, so Altiward can't run alongside altiward-forwarder's on-Mac hook. Its relay works with either.

The Altiward server can also read Intune's list of Macs through Microsoft Graph, read-only, with one application permission: each Mac's serial number, name, primary user and last check-in. It never changes anything in Intune. See Connect Intune in the install guide.

Keep the managed admin account separate

If Intune creates a local admin account at enrollment, put its short name in PermanentAdmins, exactly as you set it in Intune. Altiward leaves listed accounts out of unexpected-admin findings, expiry enforcement and the removal of admin rights nobody granted. Left out, the account shows as an admin nobody granted, and with OutOfBandEnforcement set to enforce Altiward removes it from the admin group. Password management stays with Intune. See how Altiward treats permanent admins.

Check the whole workflow

On a pilot Mac with both Privileges and Altiward:

  1. Confirm that the Mac enrolls and appears in the console's Fleet view.
  2. Request admin through SAP Privileges with a test reason. Check that Altiward records the user, Mac, reason and expiry.
  3. End the session and confirm that the admin rights and console record agree.
  4. Test your chosen expiry policy and console revocation while the Mac can reach the server.
  5. Confirm delivery to your SIEM using the Altiward SIEM guide.
