When SAP Privileges admin rights outlive the timer

SAP Privileges takes admin rights away with a countdown that runs in the person's own session. Six things can leave those rights in place after the timer ends. Settings in your Privileges profile fix most of them; the rest need a check that runs outside the session.

Last reviewed October 2026SAP Privileges 2.6.0corp.sap.privileges

The short answer

  1. No limit was set, so people chose Never or kept renewing. Set ExpirationIntervalMax.
  2. The person isn't covered by LimitToUser, LimitToGroup or an exclusion list, so they have no timer at all.
  3. Something other than Privileges changed the admin group. Privileges logs that but doesn't undo it.
  4. The person used their admin rights to keep them, for example by creating a second admin account. No setting prevents this.
  5. A grant reported an error but went through without a timer, in some reported cases.
  6. The profile didn't apply, usually because it targets the wrong preference domain.

This guide was checked against Privileges 2.6.0, released on 17 September 2026. Key names are the ones you set in a configuration profile for the corp.sap.privileges preference domain. Jump to the profile to start from, or read on for each cause.

How the timer works

When someone asks for admin, PrivilegesDaemon, which runs with root rights, adds them to the Mac's admin group. The countdown that should take them out again is run by the PrivilegesAgent, a LaunchAgent in the person's own session. SAP's maintainers put it this way: "the revocation of admin rights happens in the user context" (issue #277).

That design is reasonable, and the agent is relaunched if it quits. But it means the thing that ends admin rights runs alongside a person who, for those minutes, can change anything on the Mac.

Six reasons admin rights outlive the timer

1. The timer was never meant to end

An ExpirationInterval of 0 "disables the timeout and allows the user to request permanent administrator privileges." Unless a profile manages the interval, people can pick Never themselves. Renewals extend a grant too: AllowPrivilegeRenewal offers a Renew button before expiry, and from 2.6.0, AutoRenewalProcessPaths renews automatically while a listed process is running. There's no cumulative cap on renewals today; it's an open feature request.

2. The person isn't covered by the timer

With LimitToUser or LimitToGroup set, people outside the limit aren't managed by Privileges at all, so an admin right they hold has no timer. SAP confirmed this is "expected behavior" in issue #277. AutomaticRevocationExcludedUsers (2.5.2+) deliberately exempts accounts from every automatic revocation, which is right for a break-glass account and wrong for anyone else.

3. Something else changed the admin group

If another process adds or removes an admin, Privileges notices but doesn't undo it. A maintainer explained why: "If the admin privileges are changed by another process, Privileges is out of the game… it's a bad idea to change them again" (issue #185). Since 2.3.0, Privileges logs the change on the Mac. From 2.6.0, on macOS 14 or later with the system extension turned on, it logs every change to the admin group along with the process that made it. That record stays on the Mac, where an admin reads it with PrivilegesCLI --history. It raises no alert and sends nothing to a SIEM. Platform SSO set to make users admin at sign-in is one example reported to SAP (issue #185).

4. The person used their admin rights to keep them

This is the one SAP is most direct about. Its FAQ lists what a local admin can do, including "completely removing the Privileges application", "creating a new administrator account or modifying existing user accounts", and "resetting date/time… to try to trick Privileges". A second admin account outlives every timer, because Privileges only manages the account that asked. Persistence through a sudoers.d entry has been reported too (issue #92).

Tamper protection (2.5.0+, below) protects Privileges' application files and components against unauthorised changes. In its discussion of a proposed cumulative elevation limit, SAP also explains that client-side controls are not a tamper-proof boundary against someone determined to misuse existing admin rights (issue #280).

5. The grant reported an error but went through

A user report in issue #288 describes a grant succeeding without a revocation timer after the daemon reports Failed to verify group membership. The reporter suspected directory cache delays on Macs signed in with an Apple Account; the maintainer discussed removing the extra verification check. Read the issue and current release notes to assess whether the report applies to your version and environment. An earlier report with the same symptom, issue #260, could not be reproduced by the maintainer.

6. The profile didn't apply

Privileges reads managed settings only from corp.sap.privileges. A profile aimed at another domain, such as the daemon's, does nothing and raises no error (issue #274). On a Mac with no managed interval, the person chooses their own, including Never.

Settings that reduce the risk

All of these go in a configuration profile for corp.sap.privileges, deployed through your MDM. SAP's Managing Privileges page documents each one.

KeySinceRisk it reduces
ExpirationIntervalMax2.0.0Lets people choose a duration up to your limit and takes Never off the table. SAP recommends it over ExpirationInterval; if you set both, ExpirationInterval wins.
AllowPrivilegeRenewal, RenewalFollowsAuthSetting2.1.0Leave renewal off, or make renewing need the same authentication as the first request.
RevokePrivilegesAtLogin2.0.0Takes admin away when the person signs in, so rights don't carry over a logout or restart.
RevokePrivilegesOnScreenLock2.5.1Ends admin when the screen locks, so an unattended Mac isn't left elevated.
RevokePrivilegesAfterSystemTimeChange2.4.1Ends admin if the clock is changed. SAP notes it "offers no protection against users misusing their admin rights" in other ways.
EnableSystemExtension2.5.0Tamper protection for Privileges' own files and launchd jobs, on macOS 13 or later. It needs Full Disk Access granted to corp.sap.privileges.extension by a PPPC profile.
RequireAuthentication, ReasonRequired1.5.0Makes each request carry a password or Touch ID, and a reason you can review later.
RemoteLogging, QueueUnsentEvents1.5.0, 2.4.0Sends each grant and revocation off the Mac, by syslog or webhook, and queues events that couldn't be sent. See sending Privileges logs to your SIEM.

Keep LimitToUser, LimitToGroup and the …ExcludedUsers keys for the accounts that genuinely need them, and remember that anyone outside them has no timer.

A profile to start from

This turns on every setting in the table except remote logging. Upload it as custom settings for corp.sap.privileges, for example in Jamf Pro's Application & Custom Settings. Intune's preference file wants the keys alone, without the first four lines or the last two; see the Intune guide.

  • 30 minutes is the longest grant people can choose. Pick the limit that fits the work.
  • Screen-lock revocation ends admin if the screen locks during a long install. Leave it out if that gets in the way.
  • The system extension also needs your MDM to approve SAP's extension (team 7R5ZEU67FQ) and give corp.sap.privileges.extension Full Disk Access. SAP's Example_ApprovePrivileges.mobileconfig does both, but it also sets two of these keys; keep them in one profile only.
  • Remote logging needs your own server details. See Privileges' own remote logging.

Checking from outside the session

SAP's FAQ says that "controls, mitigations, defense-in-depth, reporting, and auditing suitable to each organization's environments and threat models are needed. This is true with or without the use of the Privileges application." Causes 3 to 5 need something outside the person's session that checks the admin group itself.

A scheduled demotion script runs as root from a LaunchDaemon and removes admin rights still held after a wait you set. Kandji publishes one as Privileges Checker, which checks every 15 minutes, and PrivilegesDemoter is a community option configured by profile. They're simple and free. They use their own wait rather than the expiry Privileges set, they act on the Mac only, and a local admin can unload them.

Altiward is ours, and it's also free and open source. It compares the admin group with the grant Privileges reported, including its expiry. By default it alerts on rights past expiry; with ExpiryEnforcement set to enforce in the com.altiward.agent profile, it removes them after a grace period, five minutes by default. It also reports admins nobody granted. It takes more to run than a script: a server, console and database you host, and an agent on each Mac. A local admin can stop the agent too, but the server then reports that Mac as no longer checking in, so a stopped check shows up as a gap rather than silence.
