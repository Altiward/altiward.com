Send macOS SAP Privileges events to your SIEM

Each time someone gains or gives up admin rights through SAP Privileges on a Mac, your SIEM can get a record of it. There are three ways to send it, from a setting in Privileges itself to a full oversight tool.

Last reviewed October 2026SAP Privileges 2.6.0Splunk · Microsoft Sentinel · syslogOCSF

This guide is about the macOS app SAP Privileges, not the security of SAP's business software.

1. Privileges' own remote logging

Since version 1.5.0, Privileges can report each change itself. Add RemoteLogging to the profile that sets corp.sap.privileges. ServerType is syslog or webhook, and ServerAddress is the syslog host or the webhook's URL. Syslog goes to port 514, or 6514 with UseTLS. QueueUnsentEvents (2.4.0 or later) keeps events Privileges couldn't send, 20 by default, and sends them again the next time someone changes their rights through Privileges.

With ServerType set to webhook, Privileges posts JSON like this example from SAP's documentation. custom_data holds whatever you put in WebhookCustomData, and delayed is true for an event sent from the queue.

Two limits decide whether this is enough on its own:

  • The webhook can't carry a token. Splunk's HTTP Event Collector and Sentinel's Logs Ingestion API both need one, so the webhook needs something in between to receive it.
  • Syslog arrives in Privileges' own format. If a syslog receiver already feeds your SIEM, this is the simplest route, but you write the parsing yourself.

2. altiward-forwarder: OCSF into Splunk or Sentinel

altiward-forwarder is free and open source. It turns each Privileges event into an OCSF record and sends it to Splunk, Sentinel or syslog. It works in one of two ways:

  • A relay you host takes Privileges' webhook, checks each Mac's client certificate and stores the event on disk before it answers. Relay quick start.
  • A hook on each Mac, which Privileges runs after each change, sends the record straight to your SIEM. There's no relay to host, but each Mac holds a token for your SIEM. Hook quick start.

Every record says verified: false, because it's what the Mac reported and nothing checks it. A local admin can stop Privileges from reporting.

3. Altiward: checked against the admin group

The Altiward agent reads each Mac's admin group and compares it with the grants Privileges reported and your permanent-admin list. The server sends the same OCSF records, plus findings for what doesn't match. CEF is also available for syslog. You choose the destination; no session evidence goes to Altiward.

Configure the server using Connect your SIEM in the install guide. Events wait in the server's Postgres outbox until the destination accepts them, so a SIEM outage delays delivery.

To check a session end to end:

  1. Request temporary admin through SAP Privileges on an enrolled Mac. Give a reason you can recognise.
  2. Find the session in the Altiward console. Check the user, Mac, recorded reason, grant time and expiry.
  3. Revoke the session while the Mac can reach the server, then confirm that its admin rights have ended.
  4. Find the corresponding events in your SIEM and compare them with the console record.

Then decide which findings need a response:

  • Admin rights without a recorded grant: check the account's purpose and your permanent-admin list.
  • Detected changes during a session: correlate new local accounts or other persistence changes with your security telemetry.
  • Rights past expiry: check your configured expiry policy and the recorded outcome. Alerting is the default; removing rights requires enforcement to be enabled.
  • Missing check-ins: investigate a loss of visibility. The finding does not establish why the Mac stopped reporting.

The console and SIEM walkthrough shows example records, and the event schema has the full contract.

Find elevations in Splunk and Sentinel

The forwarder and Altiward write to the same places: Sentinel's AltiwardOCSF_CL table and Splunk's altiward:ocsf sourcetype. So these searches, from altiward-siem, list every grant from either one, with its reason, expiry and which product reported it.

Forwarder webhook events name the Mac only by its hardware UUID, so DeviceSerial is empty for them. altiward-siem also has alerts, such as more than 10 elevations by one user in 7 days and one user's admin time per day over a limit. Each says whether it works with forwarder events or needs Altiward.
